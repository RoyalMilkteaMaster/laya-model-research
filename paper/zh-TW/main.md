## 摘要（Abstract）

<!-- EN: §0 ¶1 -->
小型語言模型（SLM）常無法妥善管理多跳問答迴圈：過早停止、不必要地檢索，或誤用工具。自適應檢索大多從生成模型本身讀取控制訊號；何時應改由外部的校準控制者接手，仍不清楚。我們研究 Laya，一個輸出經過校準的精簡非自迴歸決策模型，把它作為控制者，在每一跳預測證據是否足夠、接下來採取哪個動作，以及還缺多少證據。2×2 因子設計固定拆解迴圈，交叉兩個因子：證據來源為閉卷回憶或帶重排的檢索增強生成（RAG），迴圈控制者為負責生成的大型語言模型（LLM）或 Laya。我們在 HotpotQA、2WikiMultihopQA 與 MuSiQue 上評估五個 Qwen3.5 模型（0.8B 到 27B 參數），每個設定 200 題。以弱標籤訓練的 Laya 在 held-out 的證據足夠性判斷上準確率達 0.9271。檢索最多讓 exact match（EM）提高 43.5 個百分點。在 RAG 下，Laya 讓 0.8B 與 2B 模型的 EM 點估計提高 1.5–9.0 個百分點，卻讓 4B–27B 模型的 EM 降低 3.5–15.5 個百分點，而 prompt token 與跳數始終較少；它最常見的錯誤是在所有黃金證據都檢索到之前就停止。因此外部迴圈控制是隨模型大小而變的準確率與效率取捨。

## 1. 緒論（Introduction）

<!-- EN: §1 ¶1 -->
大型語言模型（LLM）受限於幻覺、參數知識過時以及對專門事實涵蓋不足。檢索增強生成（RAG）[lewis2020rag] 讓生成模型以從外部語料庫檢索到的段落為條件作答；稠密搜尋再加上 cross-encoder 重排器，能在多種 LLM 上進一步提升問答（QA）準確率 [yang2025enhancing]。

<!-- EN: §1 ¶2 -->
多跳問題要串接兩份以上文件中的事實，例如先解出一個橋接實體，再查詢它的屬性 [yang2018hotpotqa, ho2020twowiki, trivedi2022musique]。只做一次檢索常會漏掉第二跳，因此 Agent 迴圈會把問題拆成子問題並逐步蒐集證據。對在地端執行的小型語言模型（SLM）而言，控制這個迴圈是弱點：Agent 可能在證據尚未齊全時就作答、在已經拿到足夠資訊後仍持續檢索，或偏離到不相干的子問題。

<!-- EN: §1 ¶3 -->
這些控制決策是小型、結構化的預測問題：*證據足夠嗎？下一步該做什麼？還缺多少證據？* 交由生成模型判斷，會讓決策品質綁定模型大小，且每一步都要花費生成 token。Laya [laya] 是一個非自迴歸的 "System 1" 決策模型，能以單次前向傳播回答型別化問題（多選一、是／否、序數分數），並為每個選項回傳一個機率；它以嚴格適當評分規則訓練，使溫度縮放能校準這些機率。多數自適應檢索方法則從生成模型讀取控制訊號，或每個查詢只決定一次（第 2 節），因此這種外部校準控制者能否取代生成模型自己的控制、這又如何取決於生成模型規模，仍是開放問題。

<!-- EN: §1 ¶4 -->
為了把迴圈與控制者分開，我們以共用拆解迴圈的 2×2 因子設計，交叉**證據來源**（閉卷回憶 vs. 以稠密檢索加重排的 RAG）與**迴圈控制者**（LLM 自己 vs. Laya）；由 Laya 控制時，它的決策在每一跳都強制執行，而不是當作可選用的工具，且所有模型一律關閉 thinking 模式。我們在三個多跳基準資料集上執行 Qwen3.5 家族 [qwen35] 的五個尺寸，每個設定 200 題（5×4×3＝60 個設定），報告 exact match（EM）、token-level F1、成本，以及 paired bootstrap 的 95% 信賴區間（CI）；對控制者另外報告 Brier 分數與期望校準誤差（ECE）。我們提出三個研究問題（RQ）。
- **RQ1（準確率）。** 在固定的拆解迴圈下，把生成模型自己的迴圈控制換成校準過的外部決策模型，是否會改變多跳 QA 的準確率（EM 與 F1）？這是否取決於證據來源？
- **RQ2（成本）。** 外部控制如何改變每題的成本：token、跳數、端到端延遲，以及工具呼叫的可靠度？
- **RQ3（規模）。** 這些效果如何隨生成模型的規模（0.8B 到 27B 參數）而改變？

<!-- EN: §1 ¶5 -->
本文的貢獻依序回答這些問題：
- 一套因子實驗框架：在同一個迴圈下分離證據來源與迴圈控制者，並以錯誤分類把每個錯答定位到工具、檢索、停止或作答階段（RQ1）。
- 一套弱監督方法：以模擬 Agent 狀態的方式，從支持段落標註訓練校準過的多跳控制器，作為 RQ1–RQ3 中的外部控制者。
- 一份地端 SLM Agent 中明確控制之成本的刻畫：token、跳數、延遲與工具呼叫可靠度（RQ2）。
- 一份涵蓋五個 Qwen3.5 尺寸與三個資料集的分析，顯示外部控制對準確率的效果會隨生成模型規模反轉（RQ3）。

<!-- EN: §1 ¶6 -->
第 2 節回顧相關研究，第 3 節說明方法，第 4 節報告結果，第 5 節回答各 RQ 並說明研究限制，第 6 節為結論。

## 2. 相關研究（Related Work）

<!-- EN: §2 ¶1 -->
**檢索管線。** RAG [lewis2020rag] 讓生成模型以外部語料庫的段落為條件作答。Yang 等人 [yang2025enhancing] 結合 BGE-M3 嵌入 [chen2024bgem3]、精確內積索引 [douze2024faiss] 與 BGE cross-encoder 重排器 [chen2024bgem3, bgerankerv2m3]，在兩個中文 QA 基準上讓 17 個 LLM 中幾乎全部得到準確率提升。我們沿用這套管線作為證據來源，並探討由誰決定何時檢索、何時停止。

<!-- EN: §2 ¶2 -->
**多跳 QA 與 Agent。** HotpotQA [yang2018hotpotqa]、2WikiMultihopQA [ho2020twowiki] 與 MuSiQue [trivedi2022musique] 都需要跨維基百科段落串接事實，並標示支持段落；前兩者以 EM 與 token-level F1 評估，MuSiQue 以答案 F1 評估。我們在三者上都報告 EM 與 F1，並用這些標註建立語料庫、衍生弱標籤與分類錯誤。AutoGen [wu2024autogen] 及其延續 AG2 [ag2] 讓 LLM 在多輪中呼叫工具；何時停止通常交給生成模型，方式是作答工具或固定步數，而工具呼叫的可靠度會隨模型大小而變。

<!-- EN: §2 ¶3 -->
**自適應與動態檢索。** FLARE [jiang2023flare] 在即將生成的句子含有低信心 token 時檢索。Adaptive-RAG [jeong2024adaptiverag] 依複雜度把每個查詢分派到不檢索、單步或迭代檢索。DRAGIN [su2024dragin] 依生成模型的資訊需求決定何時檢索、檢索什麼。SeaKR [yao2025seakr] 依生成模型內部狀態的不確定性觸發檢索。這些方法的訊號來自生成模型，或每個查詢只決定一次。S2G-RAG [li2026s2grag] 加入逐輪判斷證據是否足夠的判斷器。RAG-on-a-Diet [ding2026ragdiet] 訓練一個強化學習 Agent，逐跳挑選足以處理該步的最小模型，並以信心門檻停止。

<!-- EN: §2 ¶4 -->
**校準決策模型。** Laya [laya] 以一次前向傳播，把文字狀態與型別化問題對應到每個選項的機率，適用於 `choice`、`noul`（是／否，回傳 P(true)）與 `score`（序數）三種問題。對「足夠」機率設門檻的控制者，在機率失準時會過早或過晚停止，因此我們報告 Brier 分數與 ECE。

<!-- EN: §2 ¶5 -->
**定位。** 決定何時檢索、何時停止是既有的研究問題，我們並不主張為此提出新的決策層。我們的控制器是校準過的非自迴歸模型，與生成模型分離，且只用弱標籤訓練；因子設計只替換證據來源與控制者；而且不同於為節省成本而在多個生成模型之間挑選的 RAG-on-a-Diet，我們把生成模型大小當作實驗因子，研究外部控制的準確率與效率取捨如何隨規模而改變。

## 3. 方法（Method）

### 3.1. 問題設定與 2×2 因子設計

<!-- EN: §3.1 ¶1 -->
給定資料集 d 中的多跳問題 q、LLM M，以及該資料集專屬的段落語料庫 C_d，Agent 維護由目前已問過的子問題與已蒐集的證據組成的狀態 s = (q, Q_sub, E)。每個條件由兩個開關定義：**證據來源** e ∈ {recall, rag}，即證據從哪裡來；**迴圈控制者** c ∈ {llm, laya}，即由誰判斷何時停止並作答；兩者交叉得到表 1 的四種條件。

<!-- EN: §3.1 ¶2 -->
**表 1：2×2 因子設計的四種條件。所有條件共用演算法 1 的迴圈。**

| 條件 | 證據來源 e | 控制者 c |
|---|---|---|
| Recall+LLM（閉卷回憶、LLM 控制） | recall（閉卷） | llm |
| RAG+LLM（檢索、LLM 控制） | rag（檢索＋重排） | llm |
| Recall+Laya（閉卷回憶、Laya 控制） | recall（閉卷） | laya |
| RAG+Laya（檢索、Laya 控制） | rag（檢索＋重排） | laya |

<!-- EN: §3.1 ¶3 -->
這個設計能分離兩個主效應及其交互作用。Recall+LLM 不是單發的閉卷作答，而是同一個迴圈：由 LLM 自己提出子問題、憑記憶回答，並自行決定何時停止；因此 llm 與 laya 之間的差異反映的是控制協定（由誰停止，以及提供哪些工具），而不是迭代拆解本身。

### 3.2. 共用拆解迴圈

<!-- EN: §3.2 ¶1 -->
演算法 1 是每個條件的迴圈：每一跳由 LLM 提出一個子問題，並以檢索或回憶加入證據；最多 H_max＝4 跳之後，或控制者停止時，LLM 依證據作答。

<!-- EN: §3.2 ¶2 -->
**演算法 1：四種條件共用的拆解迴圈；檢索段落依段落 id 去重，且上限 |E| ≤ 8。**

```text
輸入：問題 q；證據來源 e ∈ {recall, rag}；控制者 c ∈ {llm, laya}；H_max = 4
Q_sub ← []；E ← []
for h = 1 … H_max:
    d_h ← ∅                                    # 除非 c = laya，否則不給提示
    if c = laya:
        d_h ← Laya(BuildState(q, Q_sub, E))
        if d_h.p_suf ≥ 0.5: break              # 強制作答
    q_h ← M.SubQuestion(q, Q_sub, E, d_h)
    if c = llm 且 M 呼叫了 final_answer:
        break
    將 q_h 加入 Q_sub
    if e = rag:
        E ← E ∪ Rerank(q_h, Dense(q_h, 20))[1:3]
    else:
        E ← E ∪ {M.Recall(q_h)}
return M.Answer(q, E)
```

<!-- EN: §3.2 ¶3 -->
**控制者。** 當 c＝laya 時，每一跳開始時呼叫 Laya。若「證據足夠」的機率 p_suf ≥ 0.5，迴圈結束，LLM 必須作答；否則把 Laya 預測的下一步動作與剩餘跳數作為提示交給 LLM，且只提供 `ask_sub_question` 一個工具。當 c＝llm 時，提供 `ask_sub_question` 與 `final_answer`，由 LLM 呼叫後者停止。停止的那一跳也計入，因此跳數等於決策次數；每題有 300 秒預算。

<!-- EN: §3.2 ¶4 -->
**證據與失敗。** 當 e＝rag 時，子問題即為查詢：稠密檢索器從 C_d 回傳前 20 段，重排後的前 3 段加入 E。當 e＝recall 時，加入的是 LLM 對子問題的閉卷回答。回覆中沒有對所提供工具的合法呼叫（包括只回純文字）時，該題以 `invalid_tool` 結束；超過預算記為 `timeout`；其他失敗記為 `error` 或 `oom`；這些都算答錯。

### 3.3. Laya 作為決策層

<!-- EN: §3.3 ¶1 -->
每一跳 Laya 對狀態回答三個固定的英文問題，每種問題型別各一個：要不要停止、下一步做什麼，以及證據距離完整還有多遠。

<!-- EN: §3.3 ¶2 -->
- `sufficient`（`noul`）：證據是否足以回答原始問題？Laya 回傳 p_suf＝P(true)。
- `next_action`（`choice`）：（A）立即作答；（B）再拆一個子問題並檢索；（C）換一個查詢再找。
- `remaining_hops`（`score`）：還缺幾段關鍵證據：0、1 或 2（兩段以上）。

<!-- EN: §3.3 ¶3 -->
**狀態組裝。** BuildState 把問題、子問題與證據組成文字狀態，每筆證據截取前兩句，總長在 900 tokens 以內；訓練與推論的狀態都由它建立，因此格式相同。

### 3.4. 以狀態模擬產生弱監督

<!-- EN: §3.4 ¶1 -->
這三個決策沒有人工標籤，但訓練切分標註了支持段落。對一個訓練問題，令其黃金段落為 G、干擾段落為 D，我們模擬四種狀態：（1）**只有問題**，E＝∅；（2）**部分黃金**，G 的一個非空真子集，加上 0–2 段 D 中的段落；（3）**全部黃金**，G 的全部，加上 0–2 段 D 中的段落，順序打亂；以及（4）**只有干擾**。

<!-- EN: §3.4 ¶2 -->
令 m＝|G \ E| 為證據中缺少的黃金段落數。標籤為：
- `sufficient` ＝ 1[m＝0]；
- `next_action` ＝ A（若 m＝0）；C（若 E ≠ ∅ 且 E ∩ G＝∅）；否則 B；
- `remaining_hops` ＝ min(m, 2)。

因此缺少黃金證據時應再拆一步，除非證據全是干擾段落，此時應換查詢重找。

<!-- EN: §3.4 ¶3 -->
我們以固定種子從每個資料集抽出 800、100、100 題訓練問題，分別作為訓練、校準與 held-out 切分，目標約 3 萬筆訓練決策。正式實驗前，決策層必須達到：`sufficient` 與 `next_action` 的準確率皆至少 0.75，且兩者都比 zero-shot 基底 checkpoint 高至少 0.20；`remaining_hops` 的平均絕對誤差（MAE）至多 0.5；zero-shot checkpoint 只用於這項檢查。

### 3.5. 評估方式

<!-- EN: §3.5 ¶1 -->
主要指標是經官方答案正規化後的 EM，並列 token-level F1（MuSiQue 取答案及其別名中的最大值）。每一題記錄端到端延遲、整張卡的 GPU 記憶體峰值、LLM 的 prompt 與輸出 token、跳數，以及 Laya 呼叫的延遲；對決策層，我們報告準確率、Brier 分數、ECE 與每次決策的延遲。EM 差異附 paired 百分位 bootstrap 的 95% CI（10,000 次重抽 200 題）。

### 3.6. 實作細節（Implementation Details）

<!-- EN: §3.6 ¶1 -->
**模型與資料集：** Qwen3.5 指令模型家族 [qwen35] 的五個尺寸（0.8B、2B、4B、9B 與 27B 參數），一律關閉 thinking，context 為 8192 tokens，greedy 解碼，種子 42，在單張 24 GB 的消費級 GPU 上執行（軟體、checkpoint 與授權見附錄 A）。資料集為 distractor 設定的 HotpotQA [yang2018hotpotqa]、2WikiMultihopQA [ho2020twowiki]（簡稱 2Wiki），以及 MuSiQue [trivedi2022musique] 的可回答子集：每個資料集從 validation 切分抽出 200 題測試題，800／100／100 題決策資料問題則從訓練切分抽出，因此決策層不會看到任何測試題。正式實驗前，每個模型回答 20 題固定的工具呼叫探針題；所有模型都保留。

<!-- EN: §3.6 ¶2 -->
**檢索：** 依照 [yang2025enhancing]，段落與子問題以 BGE-M3 [chen2024bgem3] 嵌入，以精確內積搜尋檢索，再以 BGE cross-encoder 重排器 [bgerankerv2m3] 重新評分。每個資料集的語料庫是其 200 題測試題的全部段落（支持與干擾）去重後的聯集，一個段落為一個 chunk。嵌入模型、重排器與 Laya 都與生成模型共用 GPU。

<!-- EN: §3.6 ¶3 -->
**控制器：** 以多語 Laya checkpoint [laya] 為起點，以 Laya「以嚴格適當評分規則進行強化學習」的流程 [laya] 微調出三個資料集共用的一個決策層，之後在校準切分上為每種問題型別擬合一個溫度（細節見附錄 A）。

## 5. 討論（Discussion）

### 5.1. 研究問題的回答

<!-- EN: §5 ¶1 -->
**RQ1（準確率）。** 在我們的設定中，Laya 的控制主要在有檢索時改變 EM，改變的方向取決於模型大小。在閉卷回憶下，它對 2B–27B 模型的 EM 改變只有 −2.0 到 +2.5 pp，這與「瓶頸在證據而非控制」的情形相符，而 0.8B 模型的點估計最多升高 8.0 pp；有檢索時，RAG+Laya 對 2B 與 0.8B 模型的 EM 點估計比 RAG+LLM 高 1.5–9.0 pp，對 4B–27B 模型則低 3.5–15.5 pp（表 3），CI 對 0.8B 模型在每個資料集上、對較大模型九組中的七組，以及對 2B 模型只在 HotpotQA 上不含零。差異出在停止：在 RAG+Laya 下，每個模型最常見的錯誤都是仍缺黃金證據時就停止，而在 LLM 控制下，多數錯誤發生在證據已涵蓋之後或用完跳數之後（第 4.4 節）。0.8B 的增益有一部分與工具協定同時出現：它的 `invalid_tool` 比率在 LLM 控制下（提供兩個工具）為 0.290–0.550，在 Laya 控制下（一個工具）為 0.000；這無法說明 2B 的增益（比率最多 0.015）。控制器的 held-out 品質（`sufficient` 準確率 0.9271、ECE 0.0626）是在模擬狀態上量測，而 2B 在 2Wiki 與 MuSiQue 上的增益並未確立。因此迴圈控制者應該與證據來源和工具協定一起評估。

<!-- EN: §5 ¶2 -->
**RQ2（成本）。** 在我們的設定中，有檢索時外部控制在每個設定中都降低了 token 與跳數成本，也降低了 0.8B–9B 模型的 p50 延遲。平均 prompt token 由 2,776–6,067 降到 1,565–2,329（表 5），每次 Laya 呼叫花 16.0–20.8 ms；除了 0.8B 模型的無效呼叫之外，工具呼叫都很可靠（一題 `error`，沒有 `oom`）。成本的節省來自較早停止：RAG+Laya 最常在第 2 跳停止（圖 5），它停止的那一跳不需要呼叫 LLM，而 LLM 控制者讓 2B 模型在有檢索時幾乎每題都跑到 H_max。在 27B 上，記憶體壓力讓延遲比較有混淆因素（執行紀錄的計算方式見附錄 A）。因此較低的成本是一致的效果，只有在準確率不下降時才值得付出（RQ3）。

<!-- EN: §5 ¶3 -->
**RQ3（規模）。** 在我們的設定中，外部控制對準確率的效果隨模型大小反轉，而它對 token 與跳數的節省在每個尺寸都成立。交互作用的點估計在三個較大模型的九組「模型×資料集」全部為負，在兩個較小模型的六組全部為正，CI 在九組負值中有六組、在六組正值中有兩組不含零。在有檢索、由自己控制時，2B 模型幾乎從不停止，4B–27B 模型則使用比在 Laya 控制下更多的跳數（例如 2Wiki 上 3.19–3.42 跳對 2.53–2.55 跳），EM 也較高。這些實驗並未分離出機制，但對 4B–27B 模型，Laya 在仍缺黃金證據時停止、之後答錯的題目有 194–230 題。可能的原因有：門檻 0.5 事先固定，而溫度停在範圍上限（5.0）；模擬狀態與檢索狀態之間的分佈偏移；以及 BuildState 的截斷遮住了橋接事實。小模型的增益則符合只提供一個工具、以及小模型不易判斷何時停止。因此外部控制者可能補足小模型較弱的自我控制，卻截短較強模型的搜尋。由於這個交叉現象只在一個模型家族、迴圈與門檻上觀察到，外部迴圈控制應該依生成模型規模分別評估，而不是假設它能一致地延伸。

### 5.2. 研究限制

<!-- EN: §5 ¶4 -->
所有模型都關閉 thinking，因此結果無法說明 Recall+LLM 與開啟 thinking 的基線相比會如何。語料庫是封閉的，由每個資料集 200 題測試題的段落組成，而不是全維基百科，這可能讓檢索比開放領域容易。每個設定只以一個種子執行一次；bootstrap 區間涵蓋題目抽樣的變異，而不涵蓋重複執行之間的變異，2 pp 以內（四題）的差異不宜過度解讀。只使用 Qwen3.5 家族與英文資料集；翻譯資料集、雲端模型、人類評估、zero-shot Laya 條件，以及把 Laya 當作段落重排器，都不在範圍內。弱標籤來自支持段落標註，共用的單一 Laya 每個資料集只用 800 題訓練，且所有結果都綁定這個共用迴圈。錯誤分類以黃金段落代表足夠的證據，但有些題目不需要全部黃金段落也能回答。由於擬合出的溫度全部碰到搜尋範圍的上限（5.0），回報的 ECE 不能說明控制器已達最佳校準。

## 6. 結論（Conclusion）

<!-- EN: §6 ¶1 -->
我們探討何時應該由明確的校準控制者取代生成模型自己對多跳檢索迴圈的控制。由支持段落標註產生的弱監督，得到一個達到所有事先登記門檻的控制器（`sufficient` 準確率 0.9271、ECE 0.0626）；檢索是最強的因素，最多讓 EM 提高 43.5 pp。**RQ1。** 外部控制主要在有檢索時改變 EM，而它的錯誤集中在所有黃金證據都檢索到之前就停止。**RQ2。** 有檢索時，Laya 在每個設定中減少了 prompt token、輸出 token 與跳數，消除了 0.8B 模型的無效工具呼叫，並降低了 0.8B–9B 模型的 p50 延遲。**RQ3。** 有檢索時，Laya 讓 2B 與 0.8B 模型的 EM 點估計提高 1.5–9.0 pp，而 4B–27B 模型在自己控制下 EM 高 3.5–15.5 pp；CI 支持 0.8B 在每個資料集上的增益，但 2B 的增益只在 HotpotQA 上得到支持。

<!-- EN: §6 ¶2 -->
因此，外部迴圈控制並非普遍有益。對最小的模型，明確的校準控制伴隨著無效工具呼叫的消失（0.8B）、較短的檢索迴圈，以及以較低成本得到的較高 EM 點估計；對較大的模型，同一個控制者較早停止，常在橋接證據到來之前就停止，雖然減少了 token 與跳數，EM 卻較低。因此在我們的設定中，外部迴圈控制表現為隨規模而變的準確率與效率取捨，它的價值應該依生成模型規模分別評估。

## 附錄 A. 實作與重現細節（Implementation and Reproducibility Details）

<!-- EN: §A ¶1 -->
**軟體與硬體。** 語言模型由 Ollama 0.34.4 提供服務（tag 為 `qwen3.5:0.8b`、`:2b`、`:4b`、`:9b`、`:27b`），執行環境為 NVIDIA GeForce RTX 4090、WSL2 中的 Ubuntu 與 Python 3.12。嵌入模型為 `BAAI/bge-m3`，重排器為 `BAAI/bge-reranker-v2-m3`，並以 CPU 上的 FAISS 平坦內積索引搜尋；由於 27B 模型完全在 GPU 上執行，60 個設定中 BGE-M3、重排器與 Laya 也都留在 GPU。資料集取自 Hugging Face（MuSiQue 為 `musique-ans`），並轉成共同 schema。AG2 1.1.0 在我們的設定中無法關閉 thinking，因此迴圈以 Ollama Python client 自行撰寫。

<!-- EN: §A ¶2 -->
**決策層訓練。** 每個模擬狀態都把證據以整段段落與只保留支持句兩種寫法呈現（MuSiQue 保留整段），讓決策層同時看過檢索式與回憶式的證據。決策層以 `convaiinnovations/laya-multilingual`（322M 參數、輸入長度 1024 tokens）為起點，以 32,451 筆模擬決策訓練、3,996 筆校準，共花 10.8 分鐘。在 Laya 的強化學習 [laya] 中，對選項 logits 加上高斯擾動作為探索，每個樣本依與弱標籤比較的嚴格適當評分規則得到獎勵，以群組基準計算優勢，並以 soft cross-entropy 項引導訓練。之後在校準切分上為每種問題型別擬合一個溫度；三者都到達 5.0，也就是搜尋範圍的上限（第 5.2 節）。

<!-- EN: §A ¶3 -->
**紀錄與後處理。** 每一題都記錄預測、對錯、逐步 trace（子問題、檢索到的段落 id、Laya 輸出）、延遲、token 數與 GPU 記憶體峰值；所有結果都來自這些記錄、探針輸出與 Laya 評估報告。後處理腳本由它們重新計算 paired bootstrap 區間（種子 20261001）、錯誤分類與所有結果表，每次輸出逐位元相同。GPU 記憶體不足的題目以 4096 tokens 的 context 重試一次，仍失敗則記為 `oom`。授權：HotpotQA 為 CC BY-SA 4.0，MuSiQue 為 CC BY 4.0，BGE-M3 為 MIT；2WikiMultihopQA、Laya、Qwen3.5 與 BGE 重排器為 Apache-2.0。

<!-- EN: §A ¶4 -->
**執行紀錄的計算。** 唯一的 `error`（9B、2Wiki、RAG+LLM）是格式錯誤的工具呼叫 XML 回覆。問了 k 個子問題後作答的題目有 k＋1 跳，除非它到達 H_max；Laya 從未在第一跳（證據為空）停止；失敗的題目計算到失敗那一跳為止，因而壓低 0.8B 模型在 LLM 控制下的平均跳數。唯一碰到 300 秒預算的兩題（2Wiki、27B、RAG+LLM）共逾時三次（其中一題兩次），並在其他題目都沒有得到的重試中完成，因此 `timeout_rate` 在所有設定都是 0。
